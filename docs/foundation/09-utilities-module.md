# 09 — وحدة المرافق (العدادات والفواتير)

**الحالة:** معتمد التصميم — ٣ أغسطس ٢٠٢٦. التنفيذ على مراحل U-1…U-5.
**النطاق:** عدادات الكهرباء والماء، قراءاتها، وفواتيرها الشهرية. **سجلّ فقط بلا أثر مالي.**

---

## ١. القرارات الثلاثة التي تحكم كل ما بعدها

**١) كيان واحد `utility_meter` بحقل `utility_type`، لا جدول لكل مرفق.**
الكهرباء والماء لهما نفس الحقول تماماً. جدولان يعنيان ازدواج كل استعلام وكل تقرير وكل سياسة RLS، ثم جدولاً ثالثاً للغاز. و`utility_type` **نصّ مع `CHECK`** لا `enum` — لأن `ALTER TYPE ... ADD VALUE` لا يعمل داخل معاملة، فيكسر التطبيق بضغطة واحدة في SQL Editor.

**٢) من يتحمّل الفاتورة يُشتقّ ولا يُدخَل.**
لا عمود `paid_by`. القاعدة (§٤) تُحسب من العقود القائمة. حقل يُدخله إنسان **سيخالف** العقود؛ وحقل يُشتقّ منها **لا يستطيع**.

**٣) لا أثر مالي في هذه المرحلة.**
لا `charge` ولا `payment` ولا كشف مالك. الفاتورة تُسجَّل ويُعرَض من يتحمّلها، وينتهي الأمر. وهذا ما يجعل شرط «دون تغيير النماذج المالية القائمة» **صحيحاً حرفياً لا مجازاً**.

> ربط الفواتير بالاستحقاقات **قرار مرحلة ثانية مستقلّ**، ولا يُتّخذ ضمناً.

## ٢. النموذج

```
utility_meter    ← العداد
utility_reading  ← القراءات (وتسجيل الاستبدال)
utility_bill     ← الفاتورة الشهرية
```

ثلاثة جداول لا ستة، وكلّها اختيارية: **عقار بلا أي عداد يعمل كما هو اليوم بلا تغيير.**

### `utility_meter`

| العمود | ملاحظة |
|---|---|
| `org_id`, `property_id` | مطلوبان **دائماً** |
| `unit_id` | **فارغ = عداد رئيسي** |
| `utility_type` | `electricity` / `water` |
| `meter_number` | المطلوب الوحيد مع النوع |
| `account_number`, `subscription_number`, `provider`, `installed_at`, `removed_at`, `notes` | اختيارية كلّها |
| `status` | `active` / `inactive` / `removed` — و«الأرشفة» في الطلب = `inactive` |
| `meter_level` | **عمود محسوب**: `main` إن كان `unit_id` فارغاً، وإلا `unit` |

**`property_id` مكرّر عمداً** مع `unit_id` — نفس نمط `contract` في المشروع، لأن RLS تحتاج نطاق العقار مباشرة بلا `join`.

**`meter_level` حُذف كحقل مُدخَل واشتُقّ.** حقل يمكن أن يخالف الواقع **سيخالفه**.

### قيود تمنع الخطأ في القاعدة لا في الكود

**أ) الوحدة يجب أن تتبع عقار العداد** — بمفتاح أجنبي مركّب لا بمشغّل:
```sql
alter table app.unit add constraint unit_id_property_uq unique (id, property_id);
-- على العداد:
foreign key (unit_id, property_id) references app.unit (id, property_id)
```
التعديل الوحيد على جدول قائم في هذه الوحدة كلها — **فهرس فريد إضافي، بلا أي تغيير سلوك**. ولأن `MATCH SIMPLE` هو الافتراضي، العداد الرئيسي (`unit_id` فارغ) يمرّ بلا فحص.

**ب) `status='removed'` ⟺ `removed_at` مُعبّأ** — قيد `CHECK`.
**ج) رقم العداد لا يتكرّر** في نفس المكتب والنوع.

### `utility_reading`
`meter_id` · `reading_date` · `value` · **`is_reset`** · `note`
واحدة لكل (عداد، تاريخ) · القيمة ≥ صفر · التاريخ ليس مستقبلياً.

### `utility_bill`
`meter_id` · `billing_month` (أول الشهر) · `previous_reading` · `current_reading` ·
`amount_halalas` · `vat_halalas` · `other_fees_halalas` · `due_date` · `paid_at` · `notes`
واحدة لكل (عداد، شهر) · المبالغ **بالهللات** كبقية المشروع.

**لا عمود `payment_status`.** «مدفوعة» = `paid_at` مُعبّأ، و«متأخّرة» = غير مدفوعة ومضى تاريخ استحقاقها. عمود يخزّن ما يمكن اشتقاقه **ينحرف عنه**.

## ٣. 🎯 قاعدة الاستهلاك — صريحة

العداد **يُستبدل** فيبدأ من صفر، و**يلتفّ** عند سقفه. `الحالي − السابق` وحده يعطي رقماً سالباً أو خيالياً.

| الحالة | الاستهلاك |
|---|---|
| لا توجد قراءة سابقة | **`NULL`** — هذه قراءة **أساس**، ولا نعرف من أين بدأ العدّاد |
| `is_reset = true` | **= القراءة الحالية** — العداد بدأ من صفر، فالقراءة **هي** الاستهلاك |
| الحالي ≥ السابق | **الفرق** |
| **الحالي < السابق** | 🔴 **`NULL` + علامة «يحتاج مراجعة»** |

### لماذا نرفض التخمين في الحالة الرابعة

الافتراض الشائع أنه التفاف، فيُحسب `(السقف − السابق) + الحالي`. **وهذا خطأ خطير:**

- العدادات الرقمية من ٥–٦ خانات؛ الالتفاف يحتاج استهلاكاً غير واقعي لوحدة سكنية.
- القراءة الأقل **في الغالبية الساحقة** خطأ إدخال أو استبدال عداد لم يُسجَّل.
- والحساب الصامت **يحوّل خطأً مطبعياً إلى فاتورة تبدو معقولة** — وهذا أسوأ من رقم فارغ، لأن الفارغ يُرى والمعقول لا يُراجَع.

**فالنظام يتوقّف ويسأل:** «القراءة أقلّ من السابقة — هل استُبدل العدّاد؟» بزرّين: «نعم، عدّاد جديد» (يضع `is_reset`) أو «تصحيح القراءة».

> الحالة الوحيدة التي تُحسب تلقائياً هي التي أخبرَنا فيها المستخدم صراحةً.

## ٤. 🎯 قاعدة «من يتحمّل» — مشتقّة بالكامل

```
لفاتورة (عداد، شهر):

  العداد رئيسي (unit_id فارغ)؟        ← مالك العقار
  وإلا:
    ابحث عن عقد على تلك الوحدة سارٍ في آخر يوم من شهر الفاتورة
      وُجد؟        ← مستأجر ذلك العقد
      لم يوجد؟     ← مالك العقار (الوحدة شاغرة)
```

**ثلاث نقاط دقّة:**

1. **العقد الساري في شهر الفاتورة، لا اليوم.** فاتورة مارس تُحمَّل على مستأجر مارس ولو خرج بعدها. الحساب على «اليوم» كان سيحمّل المستأجر الجديد فواتير سلفه.
2. **آخر يوم من الشهر** هو المرجع، لأن الفاتورة تصدر بنهايته.
3. **تغيّر المستأجر خلال الشهر** → يُؤخذ عقد آخر الشهر **ويُعرض تنبيه**: «تغيّر المستأجر خلال هذه الفترة». **التوزيع النسبي قرار مرحلة ثانية** — لا يُخمَّن.

---

## ٥. الأمان

- RLS على الثلاثة بـ **`has_property_access(org_id, property_id)`** — نفس ما يحكم `contract`. فعضو مقيَّد بعقارات معيّنة **لا يرى عدادات غيرها**.
- الصلاحيات: `view` للقراءة، `manage_data` للكتابة — كالمستأجرين والعقارات.
- **لا `delete`** للمستخدمين: حذف ناعم كبقية المشروع.
- كل عرض (`view`) يُنشأ بـ **`security_invoker = true`** — وإلا لعمل بصلاحيات مالكه **وتجاوز RLS بالكامل**.

## ٦. الواجهة

**«المرافق» بند رئيسي مستقلّ** في الشريط الجانبي — **لا داخل الصيانة**: العدادات مرافق لا أعطال، والصيانة نفسها لم تُبنَ بعد.

```
المرافق
  ├── العدادات   ├── القراءات   ├── الفواتير   └── التقارير
```

**وفي صفحة العقار:** العدادات الرئيسية + عدادات الوحدات، مفصولتين، مع عمود «عدّادات» في جدول الوحدات.

> **لا صفحة وحدة مستقلّة في النظام اليوم** (`/app/units` شبكة بطاقات فقط). فعدادات كل وحدة تُعرَض من تبويب العقار ومن تصفية شاشة القراءات، ويُنقل القسم إلى صفحة الوحدة يوم تُبنى.

**نموذج إضافة عداد = ثلاثة حقول ظاهرة** (النوع · الرقم · الوحدة أو «رئيسي»)، والباقي تحت «تفاصيل إضافية» — احتراماً لأن **المكتب يُدخل أرقام العدادات فقط**.

## ٧. التقارير الأربعة

| # | التقرير |
|---|---|
| ١ | **الفواتير المستحقة** — غير مسدّدة ولم يمرّ تاريخها |
| ٢ | **الفواتير المتأخرة** — غير مسدّدة ومضى تاريخها |
| ٣ | **الاستهلاك الشهري** — اتجاه ١٢ شهراً لكل عداد/عقار |
| ٤ | **عدادات تحتاج انتباهاً** |

**التقرير الرابع أُعيد تعريفه بقرار المالك.** «العدادات غير المرتبطة» فقد معناه بعد اشتقاق `meter_level`: العداد بلا وحدة **هو** عداد رئيسي، وهذا طبيعي لا خلل. التعريف العملي بدلاً منه:

- عدّاد نشط **بلا قراءة منذ ٦٠ يوماً**
- فاتورة **بلا قراءة** تسندها
- **وحدة مؤجَّرة بلا عدّاد**
- قراءة **موسومة «يحتاج مراجعة»** لم تُحسم

> تقرير يقود إلى فعل، بخلاف الأول الذي كان يعرض وضعاً سليماً.

## ٩. معايير القبول

- [ ] الستّة سيناريوهات تعمل: رئيسي واحد · عدّة رئيسية · لكل وحدة · مزيج · عدّادان لنفس الوحدة · عقار بلا عدادات
- [ ] عدّاد وحدة من عقار آخر **مرفوض من القاعدة**
- [ ] رقم عدّاد مكرّر في نفس المكتب والنوع **مرفوض**
- [ ] قراءة أقلّ من سابقتها → `NULL` + علامة مراجعة، **ولا رقم مخمَّن**
- [ ] بعد وسمها «عدّاد جديد» → الاستهلاك = القراءة الحالية
- [ ] فاتورة على وحدة مؤجَّرة → **مستأجر ذلك الشهر** لا الحالي
- [ ] فاتورة على وحدة شاغرة أو عدّاد رئيسي → **مالك العقار**
- [ ] عضو مقيَّد بعقار **لا يرى** عدادات عقار آخر
- [ ] **لا يُنشأ أي `charge` ولا يتغيّر أي رصيد**
